Build this document with the **고객 제안서** format. The reader is the client's approver.
The layout adds the cover head (고객사·사업명·제안사·제안일·담당자·연락처·유효기간) and the
section numbers.

- If the client gave a table of contents in an RFP or 제안요청서, follow that table of
  contents and order exactly.
- Without one, write in the order 제안 요약 → 고객 과제 이해 → 제안 내용 → 요구사항 대응표 → 추진 일정
  → 수행 조직·투입 인력 → 견적 → 전제·제외 범위·위험 → 요청 사항.

## 고객에 관해 쓰기

- Write the client's current state, tasks, budget, schedule and requirements only as stated
  in the RFP and the material. Do not fill with generalities (「디지털 전환 시대에…」).
- 고객 과제 이해 opens by quoting at least one of the client's own words (RFP wording,
  meeting remarks) in quotation marks.
- 요구사항 대응표 is a table (요구 ID | 요구 내용 | 대응 방안 | 제안서 위치); do not leave out a
  single requirement ID from the material.

## 견적

- Under the table (항목 | 수량 | 단위 | 단가 | 금액 | 비고) put 공급가액·부가세·합계 rows.
  금액 = 수량 × 단가, 합계 = 공급가액 + 부가세.
- State 부가세 포함·별도 above the table, and compare with the budget only on the same basis.
  If the budget is exceeded, say so; do not change unit prices — offer a separate
  scope/period adjustment.

## 제안사에 관해 쓰기

- Write track record, certifications, awards and reference clients only as found in the proposer's material. If missing, leave brackets like 「[수행 실적]」 「[인증]」.
- Do not write promises such as 「보장」 「100%」.
- When sources disagree (period, amount), state which one you assumed and leave it as a question in 요청 사항.
- Put the client's own tasks (자료 제공·계정 발급·검수) in the schedule too; dates not in the material are 「협의」.
- Close the last section with one line stating the decision you ask the client to make.
- Wrap anything whose meaning survives only when copied character for character — system names, identifiers, paths — in `<code>`.
